# 图片附件：直接视觉输入

本次只支持 PNG、JPG/JPEG，直接调用当前所选模型的视觉能力，不增加 OCR、PDF 或图片读取工具调用。

## 职责与源码对应

DeerFlow 的 `ViewImageMiddleware` 在模型调用前将图片组织成视觉消息；Mini Deer
复用同一职责边界，由 `prepare_model_messages` 将已验证附件投影为 `image_url`。
本项目从用户附件直接进入视觉输入，不经过 `view_image` 工具。

选择附件 → 前端缩略图及编码 → 正式 Run 请求 → 后端校验实际格式和像素 →
消息附件持久化 → 模型调用前的视觉投影 → 流式回答。

用户原问题保留纯文本，图片保存为标准 data URL；既有 `filename/content` HTTP
字段及数据库旧表结构保持兼容。历史响应按媒体类型还原图片，可以展开或下载。
下载通过同源 HTTP 接口按消息 ID 和附件序号返回原始字节，复用本地来源检查，
不依赖浏览器对 data URL 或 Blob 下载的兼容情况。
摘要只保存图片来源元数据和已有对话结论，不把 Base64 作为文字送给摘要模型。

## 浏览器验收

1. 打开 `http://127.0.0.1:5173/`，新建对话，选择“环境默认”或 `glm-5.3-flash`。
2. 点击“+ 附件”，选择 PNG 或 JPG/JPEG，预期出现缩略图、文件名、原始文件大小及移除按钮。
3. 输入关于图片的问题并发送，预期模型能够根据真实图像回答，不需要先调用 OCR。
4. 不输入问题，仅选择图片发送，预期自动使用“请描述附件中的图片。”。
5. 点击消息附件展开原图或下载；刷新页面，再次检查图片和下载入口仍可用。
6. 混合选择文本和图片，预期都进入同一条消息；超过 3 个附件时明确拒绝。
7. 检查错误提示：单图超过 4 MiB、损坏文件或伪装图片应被拒绝；PDF 仍不受支持。

## 输入框粘贴图片

DeerFlow 对照：`frontend/src/components/ai-elements/prompt-input.tsx` 的
`handlePaste` 从剪贴板提取文件并交给 `attachments.add`。
Mini Deer 的 `Composer.handlePaste` 提取图片并交给共用的 `addAttachments`，
再由 `prepareSelectedAttachments` 校验、解码并生成待发送缩略图。
选择文件和粘贴使用同一条读取队列，连续粘贴时顺序合并；读取失败保留先前附件。
后续 Run 请求、持久化和模型视觉输入完全复用图片附件链路。

1. 截图或复制图片内容，点击聊天输入框并按 `Ctrl+V`，预期出现一个待发送缩略图。
2. 再粘贴普通文字，预期在光标处插入文字，图片仍保留；只有图片时也能发送。
3. 连续粘贴图片，预期依次添加；附件总数超过 3 个时提示超限，先前附件不丢失。
4. 点击缩略图旁的移除按钮，预期能移除该图片并继续添加。
5. 粘贴不支持的图片格式或超过 4 MiB 的图片，预期提示错误；之后仍能添加有效图片。

本机已通过浏览器真实剪贴板和 `Ctrl+V` 验证 PNG 缩略图及普通文字插入，
并保留未发送的图文草稿供检查。新增 6 项测试覆盖连续粘贴、数量限制、失败恢复、
格式和大小检查、剪贴板兼容及禁用状态；前端全部 347 项测试、Lint、类型检查及构建通过。
此项等待用户实际验收。

## 当前边界

- 每条消息最多 3 个附件；单张图片最多 4 MiB，图片合计最多 8 MiB。
- 图片单边最多 6000 像素，总像素最多 1600 万；不自动压缩或改变用户原图。
- 文本仍保持单个 32 KiB、合计 64 KiB 的既有限制。
- 当前面向已配置的 DeepSeek Flash 和 GLM-5.3-Flash。后续扩展其他模型时，再添加独立能力声明。
- 当前小图随消息内联存储；后续 PDF 和大文件上传可另建独立文件存储入口。
